### Задание 1. Резервное копирование

#### Кейс

Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.<br>

Необходимо описать, какие варианты резервного копирования подходят в случаях:<br>
1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.<br>
1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.<br>
1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.<br>

Приведите ответ в свободной форме.<br>

### Ответ

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день<br>
<br>
Для решения этой задачи подойдёт полное резервное копирование (Full Backup).<br>
Полное резервное копирование подразумевает создание копии всех данных базы на определённый момент времени.<br>
Например: Можно настроить автоматическое создание резервной копии каждый день в 23:59. В случае сбоя базы данных можно восстановить её состояние на конец предыдущего дня.<br>

Преимущества данного способа:<br>
 - Простота настройки и восстановления.<br>
 - Для восстановления достаточно одной полной резервной копии.<br>
 - Нет необходимости собирать данные из нескольких резервных копий.<br>

Недостаток — большой объём резервных копий и возможная потеря данных, созданных после последнего копирования.<br>
<br>
<br>
1.2. Необходимо восстанавливать данные за час до предполагаемой поломки<br>
<br>
Для решения этой задачи подойдёт восстановление на определённый момент времени (Point-in-Time Recovery, PITR).<br>
Этот механизм позволяет восстановить базу данных до конкретного момента времени, используя полную резервную копию и журналы изменений.<br>
Например, если сбой произошёл в 15:00, а нам необходимо восстановить состояние базы на 14:00, мы можем восстановить последнюю полную резервную копию и применить журналы изменений до 14:00.<br>
В PostgreSQL для этого используется механизм WAL (Write-Ahead Log), а в MySQL — бинарные журналы (Binary Log).<br>
Также можно использовать полное резервное копирование один раз в сутки и инкрементное каждый час. Однако PITR обеспечивает более гибкое восстановление, поскольку не ограничивается временем создания очередной копии.<br>
Такой способ позволяет уменьшить потенциальную потерю данных, но требует правильной настройки хранения журналов изменений. <br>
<br>
<br>
1.3. Возможно ли моментальное переключение на работающую базу данных при поломке основной?<br>
<br>
Да, такой механизм существует. Он называется Failover (аварийное переключение) и используется в системах высокой доступности (High Availability, HA).<br>
Для реализации можно использовать репликацию базы данных.<br>
Например, есть два сервера:<br>
 - Primary — основной сервер базы данных, который обрабатывает запросы и изменения данных.<br>
 - Replica (Standby) — резервный сервер, который получает изменения с основного сервера.<br>
При выходе основного сервера из строя система обнаруживает неисправность и переключает работу на резервный сервер.<br>
Автоматическое переключение может выполняться специальными средствами управления кластером, например Patroni для PostgreSQL или MySQL InnoDB Cluster для MySQL.<br>
Однако переключение не обязательно происходит мгновенно: обычно требуется некоторое время на обнаружение неисправности, выбор нового основного сервера и перенаправление подключений.<br>
Вывод: репликация и автоматический Failover позволяют значительно сократить время простоя. При этом репликация не заменяет резервное копирование, поскольку ошибочное удаление или повреждение данных также может распространиться на реплику<br>

### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).<br>
2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?<br>

Приведите ответ в свободной форме.<br>

### Ответ

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).<br> 
Пример создания резервной копии базы данных netology:

```
pg_dump -U postgres -Fc -f /backups/netology.dump netology
```
Описание параметров:
 - -U postgres — пользователь PostgreSQL.
 - -Fc — создание резервной копии в специальном архивном формате (Custom).
 - -f /backups/netology.dump — путь к файлу резервной копии.
 - netology — название базы данных.

Для восстановления сначала создадим пустую базу данных:

```
createdb -U postgres netology_restore
```
Затем восстановим данные:
```
pg_restore -U postgres -d netology_restore /backups/netology.dump
```
 - -d netology_restore указывает базу данных, в которую будут восстановлены данные из архива.<br>

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?<br>

Да, процесс можно автоматизировать с помощью Bash-скрипта и планировщика заданий cron в Linux.<br>

Например, создадим скрипт /usr/local/bin/backup_postgres.sh:<br>

```
#!/bin/bash

set -e

BACKUP_DIR="/var/backups/postgresql"
DATE=$(date +%Y-%m-%d)

pg_dump -U postgres -Fc \
  -f "$BACKUP_DIR/netology_$DATE.dump" netology
```
Скрипт создаёт резервную копию базы данных netology, добавляя к имени файла текущую дату.

Предварительно необходимо создать каталог для резервных копий и предоставить права пользователю postgres

### Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.<br>
3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?<br>

Приведите ответ в свободной форме.<br>

### Ответ

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.<br>
Сначала создадим полную резервную копию:

```
mysqlbackup --defaults-file=/etc/mysql/my.cnf --backup-dir=/backups/mysql/full backup
```

После этого создадим инкрементную резервную копию:
```
mysqlbackup --defaults-file=/etc/mysql/my.cnf \
  --incremental \
  --incremental-base=dir:/backups/mysql/full \
  --incremental-backup-dir=/backups/mysql/incr1 \
  backup
```

Описание параметров:
 - --incremental — включает инкрементное резервное копирование.
 - --incremental-base — указывает предыдущую резервную копию, относительно которой определяются изменения.
 - --incremental-backup-dir — каталог для сохранения новой инкрементной копии.
 - backup — команда создания резервной копии.

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?<br>
<br>
Использование репликации MySQL даёт преимущества в случаях, когда необходимо обеспечить высокую доступность базы данных, сократить время простоя и снизить нагрузку на основной сервер.<br>
Например, если финансовая компания использует базу данных для обработки большого количества транзакций, восстановление из обычной резервной копии может занять значительное время.<br>
При использовании репликации изменения постоянно передаются с основного сервера (Primary) на резервный (Replica).<br>
Если основной сервер выйдет из строя, можно переключить работу приложения на реплику, подготовленную для выполнения роли основного сервера. При правильно настроенном автоматическом переключении простой будет значительно меньше, чем при полном восстановлении из резервной копии.<br>

Дополнительные преимущества репликации:
 - Снижение нагрузки. Часть запросов на чтение можно перенести на реплику.
 - Быстрое восстановление работоспособности. При сбое основного сервера можно использовать резервный экземпляр.
 - Резервное копирование без существенной нагрузки на Primary. Полные резервные копии можно создавать с реплики.
 - Повышение доступности. Плановое обслуживание основного сервера можно выполнять с минимальным временем простоя при наличии соответствующей инфраструктуры.
При этом репликация имеет недостатки. Например, при асинхронной репликации возможна задержка передачи изменений. Кроме того, ошибочное изменение или удаление данных на основном сервере может автоматически повториться на реплике.<br>
Поэтому для финансовой компании оптимально использовать репликацию совместно с регулярным резервным копированием, а не вместо него.
